WHAT THIS IS
------------
This is a patched LinuxCNC whose trajectory planner (TP) has been rebuilt around
a jerk-limited S-curve motion profile (originally driven by the Ruckig library).
On top of that base we made five changes that, together, give a fast, smooth,
production-grade planner with a clean operator control surface:

  1. Eliminated a servo-time / following-error PEAK on dense G-code.
  2. Added a runtime CORNERING-AGGRESSIVENESS knob  (SCURVE_PEAK_SCALE).
  3. Made the TRAPEZOIDAL <-> S-CURVE switch safe (no jerk shock mid-motion).
  4. Exposed it all from G-code through one Fanuc-style dial:  G64 ... R<value>.
  5. Added native RTCP / 5-axis tool-center-point activation:  G43.4 / G49
     (Fanuc-style TCP on/off riding LinuxCNC's switchable-kinematics framework).

The machine runs the global Debian package "linuxcnc-uspace" (installed with
dpkg). The same patched source builds both that package and the run-in-place
(RIP) tree.

Two planner styles exist in this build:
  * planner_type 0  =  TRAPEZOIDAL   (bounded acceleration, jerk not limited;
                                       Siemens calls this "BRISK")
  * planner_type 1  =  S-CURVE       (jerk-limited, smoother, less machine
                                       stress; Siemens calls this "SOFT")


================================================================================
QUICK START  —  how to use it day to day
================================================================================

FROM G-CODE (recommended; put it at the top of the program):

    G64 P0.01 Q0.01 R0      ; continuous mode, TRAPEZOIDAL planner
    G64 P0.01 Q0.01 R0.5    ; continuous mode, S-CURVE, faithful cornering
    G64 P0.01 Q0.01 R1.0    ; continuous mode, S-CURVE, full cornering
    G64 P0.01               ; continuous mode, planner LEFT UNCHANGED (no R)

  R is a single "smoothness / aggressiveness" dial:
       R omitted    -> leave the planner exactly as it was (modal)
       R = 0        -> trapezoidal planner
       R = 0.1..1.0 -> S-curve planner, with cornering peak scale = R
       R > 1.0      -> S-curve planner, clamped to 1.0
  (P = path blending tolerance, Q = naive-CAM tolerance, both unchanged from
   stock LinuxCNC. R is our extension.)

FROM HAL (live tuning while running):

    halcmd setp ini.traj-planner-type 1            ; 0 = trapezoidal, 1 = S-curve
    halcmd setp ini.traj-scurve-peak-scale 0.8     ; 0.1 .. 1.0 cornering scale
  (Exact pin names: verify once with  `halcmd show pin | grep -i scurve` ;
   LinuxCNC's inihal exposes them with dashes, prefixed "ini.".)

FROM THE INI FILE (startup defaults), in the [TRAJ] section:

    [TRAJ]
    PLANNER_TYPE       = 1        # 0 = trapezoidal, 1 = S-curve
    SCURVE_PEAK_SCALE  = 1.0      # 0.5 = faithful .. 1.0 = full cornering

NOTE on when a switch takes effect:
  Changing the PLANNER TYPE while the machine is moving does NOT take effect
  instantly (that would cause an acceleration shock). It is DEFERRED and applied
  the moment motion next goes idle (program end, pause, M0/M2). While idle, a
  switch is instant. If you flip it during motion you will see a one-time
  operator message in the GUI:
        "planner switch deferred until motion stops (requested type N)"
  This is why the recommended pattern is to set G64 ... R at the TOP of the
  program, where the machine is idle and the switch is instant.


================================================================================
THE FOUR CHANGES  (detail)
================================================================================

--------------------------------------------------------------------------------
1) SERVO-TIME / FOLLOWING-ERROR PEAK  —  ELIMINATED
--------------------------------------------------------------------------------
SYMPTOM
  On large/dense programs (e.g. 150k+ tiny segments, tight finishing zones) the
  servo-thread execution time PEAKED and joints threw following-error spikes.
  It was pure RT compute cost, not disk, graphics, or kernel.

ROOT CAUSE
  The look-ahead / blend optimizer was performing full Ruckig ROOT-SOLVES every
  servo cycle (roughly 4-8 solves per cycle), and the per-solve cost exploded on
  very short / degenerate segments. The culprits were the velocity queries
  findSCurveMaxStartSpeed, findSCurveVSpeed (reached via the static-inline
  findSCurveVPeak in blendmath.h, including the arc/blend path), and
  calcSCurveSpeedWithT.

FIX
  Every one of those Ruckig velocity solves was replaced with a CLOSED-FORM
  ANALYTIC S-curve formula. The analytic forms were proven bit-identical to the
  original solver across the full input range with an offline test harness
  (src/emc/tp/scurve_analytic_test.c). Result: zero look-ahead/blend solves on
  both straight (G1) and arc (G2/G3) sections, and a flat servo-thread time.
  A small preallocated Ruckig "planner pool" remains for the legitimate
  per-segment execution planning (tiny, necessary).

NOTE — a real bug found and intentionally PRESERVED
  The original findSCurveVSpeed returned HALF the true rest-to-rest peak
  velocity, making the planner ~2x over-conservative at corners. The analytic
  replacement is physically correct. To keep behaviour identical by default, the
  faithful path scales the analytic result back by 0.5 — and the new
  SCURVE_PEAK_SCALE knob (change #2) lets you dial that 0.5 -> 1.0 to recover the
  full, physically-correct cornering speed.

KEY FILES
  src/emc/tp/sp_scurve.c , blendmath.c , blendmath.h , tp.c , tc.c ,
  ruckig_wrapper.c/.h  (+ offline proof: scurve_analytic_test.c)

--------------------------------------------------------------------------------
2) SCURVE_PEAK_SCALE  —  runtime cornering-aggressiveness knob
--------------------------------------------------------------------------------
WHAT
  A single float that scales the S-curve rest-to-rest peak velocity — i.e. how
  aggressively the machine is allowed to corner within its jerk/accel limits.
       0.5  = "faithful": reproduces the original (halved) behaviour exactly
       1.0  = "full":     physically-correct ~2x cornering
  It can be ramped 0.5 -> 1.0 on real cuts while watching following-error
  (FERROR), surface finish, and vibration.

HOW TO SET
  INI:  [TRAJ] SCURVE_PEAK_SCALE = <0.1..1.0>   (default 0.5 = no behaviour change)
  HAL:  halcmd setp ini.traj-scurve-peak-scale <0.1..1.0>   (live)
  G-code: via the R word on G64 (see change #4)

KEY FILES
  motion.h , command.c , taskintf.cc , emc.hh , initraj.cc ,
  inihal.hh/.cc , mot_priv.h , sp_scurve.c

--------------------------------------------------------------------------------
3) PLANNER-TYPE SWITCH  —  defer-until-idle + GUI notice
--------------------------------------------------------------------------------
PROBLEM
  planner_type (0 trapezoidal / 1 S-curve) is read every servo cycle, so flipping
  it mid-motion re-routed the segment in flight between the two update paths. The
  position and velocity stay continuous (no following-error fault), BUT the
  ACCELERATION jumps — a jerk impulse, exactly what the S-curve planner exists to
  avoid. The original code applied the switch immediately ("can do it any time").

FIX  —  defer-until-idle, never abort
  * If the machine is IDLE (TP queue empty): the switch is applied INSTANTLY.
  * If the machine is MOVING: the request is LATCHED and applied automatically
    the moment motion next goes idle. Motion is NEVER aborted to force it.
  * A one-shot operator message appears in the GUI when a switch is deferred:
        "planner switch deferred until motion stops (requested type N)"
    and a log line confirms when it is later applied.
  Implementation is ABI-neutral (no shared-struct changes) and lives entirely in
  the motion controller.

KEY FILES   (search tag:  PLANNER_SWITCH_DEFER)
  src/emc/motion/command.c , control.c , mot_priv.h

--------------------------------------------------------------------------------
4) G64 ... R  —  native G-code planner dial (Fanuc / Siemens style)
--------------------------------------------------------------------------------
WHAT
  An optional R word on G64 selects the planner mode AND cornering aggressiveness
  in one dial, mirroring how industrial controls expose this (Siemens SOFT/BRISK,
  Fanuc G05.1 ... Rn). Because it rides on G64, it is modal and reads naturally
  alongside the existing P (path tolerance) and Q (naive-CAM tolerance) words.

      R omitted     -> planner unchanged
      R <= 0        -> trapezoidal (planner_type 0)
      0 < R <= 1.0  -> S-curve (planner_type 1), scurve_peak_scale = R
      R  > 1.0      -> S-curve, scurve_peak_scale clamped to 1.0

HOW IT WORKS (for maintainers)
  The planner mode is carried on the EMC_TRAJ_SET_TERM_COND NML message that G64
  ALREADY emits — two new, sentinel-defaulted fields (planner_type = -1,
  scurve_peak_scale = -1.0; <0 means "unchanged"). This means:
    * it is applied in PROGRAM ORDER (not at parse/look-ahead time), and
    * it lands cleanly through the defer-until-idle guard from change #3.
  No new NML message type was added. All existing callers of the control-mode
  canon (G61, G61.1, cutter-comp save/restore) are unaffected by the defaults.
  Validated: the standalone and installed interpreters emit the correct
  SET_PLANNER_MODE(...) for R0 / R0.5 / R1.0, and R on a non-G64 line still
  correctly errors (the legality change is scoped to G64 only).

KEY FILES   (search tag:  G64_R_PLANNER)
  src/emc/nml_intf/emc_nml.hh  (2 new message fields + ctor)
  src/emc/nml_intf/emc.cc      (NML serialization update())
  src/emc/nml_intf/canon.hh    (SET_MOTION_CONTROL_MODE + 2 defaulted args)
  src/emc/task/emccanon.cc     (real canon -> sets the message fields)
  src/emc/sai/saicanon.cc      (standalone-interp echo)
  src/emc/rs274ngc/gcodemodule.cc  (preview module no-op)
  src/emc/task/emctaskmain.cc  (applies it: calls emcTrajPlannerType /
                                emcTrajSetScurvePeakScale in program order)
  src/emc/rs274ngc/rs274ngc_interp.hh , interp_convert.cc  (R -> mode mapping)
  src/emc/rs274ngc/interp_check.cc     (make R legal on G64)


--------------------------------------------------------------------------------
5) G43.4 / G49  —  native RTCP (tool-center-point) on/off, Fanuc style
--------------------------------------------------------------------------------
WHAT
  On a 5-axis (or 4-axis tilting) machine, RTCP/TCP mode keeps the TOOL TIP on
  the programmed path while the rotary axes tilt/rotate — the linear joints
  automatically compensate. Industrial controls call this Fanuc G43.4, Siemens
  TRAORI, Heidenhain M128. This build adds the Fanuc-style codes natively:

      G43.4 H<n>   -> tool-length offset from tool table entry n, then switch
                      the kinematics to TCP mode (switchkins type 1)
      G49          -> cancel the offset and return to IDENTITY kinematics
      G43.5        -> reserved (vector TCP), currently errors "not implemented"

REQUIREMENTS (all enforced or guarded in code)
  * A switchkins-CAPABLE kinematics module loaded with the identity-first
    convention: type 0 = identity (startup default), type 1 = TCP. Stock
    modules: load with  sparm=identityfirst  (e.g. xyzac-trt-kins); the
    xyzab_tdr_kins sim comp is already built this way. G43.4 on a
    non-switchable kins (e.g. trivkins) produces a clear GUI error.
  * A MEASURED tool: G43.4 with an all-zero tool length is REFUSED ("load a
    measured tool") — a zero length in TCP means the tip math is wrong.
  * Cutter compensation (G41/G42) must be off.
  * The machine's rotation-point/pivot offsets must be configured (the kins
    module HAL pins, e.g. xyzac-trt-kins.x-rot-point / .tool-offset).
  * To COMBINE TCP with the S-curve planner (G64 R>0): every axis used needs
    a jerk limit — [TRAJ]MAX_LINEAR_JERK plus per-axis [AXIS_*]MAX_JERK
    (rotary axes included!). Without it the planner falls back to trapezoidal
    for those segments and warns once.

BEHAVIOUR / SAFETY (matches the defer/queue discipline of change #3)
  * The switch is applied IN PROGRAM ORDER, only after previous motions have
    completed (it rides the same queued message as the tool-length offset,
    which task gates on motion-done). It never aborts and never jumps — the
    switch itself commands zero motion.
  * STATELESS: G43.4 always requests TCP, G49 always requests identity. After
    an abort the machine keeps its current mode; the next G49/G43.4 forces a
    known state. A TOOL CHANGE lands back in identity (the internal G49), so
    G43.4 must be re-issued per tool — exactly like Fanuc.
  * The old M428/M429-style remap path (HAL pin motion.switchkins-type) keeps
    working alongside: the pin is now EDGE-triggered, commanded switch wins
    on a tie.
  * Observables: the kins comp prints "kinematicsSwitch(): type=N" on every
    switch; kinstype.is-0/is-1 HAL pins show the active mode (wire to GUI).

VALIDATED (2026-06-10, xyzab-tdr dual-rotary sim)
  Round-trip switching with no position jump; tool tip holds position during
  pure A/B rotary moves; combined with G64 R1.0 (S-curve) cleanly; all guards
  (zero tool, cutter comp, precedence) fire correctly.

  src/emc/rs274ngc/interp_internal.hh , interp_array.cc , interp_check.cc ,
  interp_convert.cc                       (parser + guards + canon call)
  src/emc/nml_intf/canon.hh , emc_nml.hh , emc.cc
  src/emc/task/emccanon.cc , emctaskmain.cc , taskintf.cc
  src/emc/sai/saicanon.cc , rs274ngc/gcodemodule.cc
  src/emc/motion/motion.h , command.c , control.c , mot_priv.h
                                          (EMCMOT_SET_SWITCHKINS_TYPE path)

RELATED FIXES found during RTCP validation
  * tp.c: the "maxjerk < 1" S-curve error used to print EVERY SERVO CYCLE
    (log storm) for segments with no jerk limit; now warns once, naming the
    likely missing INI items, and falls back to trapezoidal as before.
  * G64 R>0 (S-curve request) is now REFUSED with a GUI message when
    [TRAJ]MAX_LINEAR_JERK is unset — parity with the INI/HAL-pin guards.
  * Sim/diagnostic note: configs that block HAL startup on a slow GUI
    (loadusr -W <vismach>) can hit "USRMOT: command timeout" at boot with
    [EMCMOT]COMM_TIMEOUT=1 on software-GL machines; raise it (e.g. 5) —
    task retries and recovers either way.

================================================================================
GLOSSARY
================================================================================
  Trapezoidal planner  Acceleration is bounded but can step instantly (infinite
                        jerk). Fast, but harsher on the machine. (Siemens: BRISK)
  S-curve planner      Acceleration is ramped at a jerk limit. Smoother, kinder
                        to the machine, slightly slower. (Siemens: SOFT)
  Jerk                 Rate of change of acceleration. Limiting it is what makes
                        S-curve motion smooth.
  Peak scale           How close to the jerk/accel-feasible maximum the planner
                        is allowed to corner (our SCURVE_PEAK_SCALE, 0.1..1.0).
  Look-ahead / blend   The optimizer that plans corner/segment velocities a few
                        moves ahead so the machine doesn't stop at every corner.
  G64                  Continuous-path (path-blending) mode. P = blend tolerance,
                        Q = naive-CAM tolerance, R = (our) planner dial.
